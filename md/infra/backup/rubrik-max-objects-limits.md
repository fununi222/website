# Rubrikの最大保護オブジェクト数は？ VMのカウント基準と限界値を徹底解説

## 超要約
[Rubrik](https://fununi222.github.io/website/html/glossary/system-glossary.html#:~:text="Rubrik") のサイジングにおいて極めて重要な「保護対象オブジェクト（Snappable）」のカウント定義と容量・ノード数に対するスケーラビリティ上限を解説します。VMware環境（1 VM = 1 オブジェクト）、DB（1 インスタンス/DB = 1 オブジェクト）の計算基準と、物理クラスタ（実質無制限スケール）と仮想エッジ（Rubrik Edgeの厳格な最大オブジェクト数キャップ）の仕様差分を整理します。

---

## 1. 「保護対象オブジェクト（Snappable）」のカウント定義

- **VMware / Hyper-V 仮想マシン**: ESXiホスト単位ではなく、**個別ゲストVMが 1 オブジェクト**。
- **データベース (SQL Server / Oracle / PostgreSQL)**: 1サーバー内であっても、独立した**各データベースが 1 オブジェクト**。
- **ファイルシステム / NAS**: 個別に定義された Fileset (ファイル共有設定) が 1 オブジェクト。

---

## 2. 物理クラスタにおけるスケーラビリティ（実質無制限）

分散メタデータストア（[CockroachDB](https://fununi222.github.io/website/html/glossary/system-glossary.html#:~:text="CockroachDB")）のシャーディング設計により、物理ノードを増強する限りオブジェクト数制限によるボトルネックは発生しません。

単一クラスタで数千〜数万規模のVM・データベースオブジェクトを統一SLAドメインで自動保護可能。

---

## 3. 仮想アプライアンス（Rubrik Edge）のハードリミット

リモートオフィス/支社向け仮想アプライアンス (Rubrik Edge) には、リソースフットプリントの仕様上明確な制限が存在します。

- **1TB 〜 5TB Edge**: 最大 **40** オブジェクト
- **5TB超 〜 10TB Edge**: 最大 **80** オブジェクト

保護対象VM・DBが80を超える環境では、仮想Edgeではなく小規模物理クラスタまたはRubrik Virtual Clusterの選定が必要です。

---

## 4. サイジングと拡張における結論

1. **カウント基準の統一**: ゲストVM数・DB数を個別に集計して算出。
2. **クラスタ選定**: 拠点オブジェクト数が80を超える場合は物理クラスタ化。
3. **将来拡張性**: 物理ノード追加による無停止スケールアウト設計を維持。
