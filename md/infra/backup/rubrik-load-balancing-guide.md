# Rubrikのバックアップ負荷分散ガイド！リソース制限ができない時の対策

## 超要約
[Rubrik](https://fununi222.github.io/website/html/glossary/system-glossary.html#:~:text="Rubrik") バックアップ運用時、本番ストレージのI/O過負荷を防ぐための設計ガイドです。ネイティブでのIngressスロットリング非対応の理由を解き明かし、OSレベルQoS、ネットワークシェーピング、SLAドメイン設計を活用した実務的アプローチを提案します。

---

## 1. なぜRubrikはバックアップ時の直接スロットリングが困難なのか？

- **受信側（Ingress）の性質**: バックアップ取得時、Rubrikはパッシブな受信ノードとして最速でのデータ保護を優先します。
- **送信側（Egress）との違い**: レプリケーションやクラウドアーカイブ通信では細かい帯域スケジュール制限が可能。

---

## 2. 本番ストレージ保護のための4つの具体策

1. **OS層でのQoS・帯域制御**: Windows / Linux エージェント側でアウトバウンド通信上限を設定。
2. **ネットワークスイッチ / vDS トラフィックシェーピング**: VMware vmkernel ポートに対し分散仮想スイッチ等で最大帯域を制御。
3. **並列チャネル数の抑制**: SLA「詳細設定」でマルチセクション・並列ジョブ数をチューニング。
4. **ストレージスナップショット連携**: ストレージアレイ機能（SAN Direct integration）へ読み出しをオフロード。

---

## 3. タスク同時実行数の制限とSLA設計

Rubrikノードごとの同時タスク数の制限（1 ESXiホスト / 1ノードあたり制限）を考慮し、バックアップウィンドウスケジュールを分散化。
