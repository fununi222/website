# AWSのデータ転送料で『クラウド破産』しないために｜200TB超えDBの最適解

## 超要約
数十TB〜200TB超のデータベースをクラウド上で運用・保護する際、最大の障害となるのが「外部データ転送費 (Egress Cost)」と「ストレージ容量・I/O上限」です。本稿では、インターネット経由のバックアップ全データ引き出しに伴う高額請求リスクと、[Amazon Aurora](https://fununi222.github.io/website/html/glossary/system-glossary.html#:~:text="Amazon%20Aurora") (Aurora Limitless Database) を用いた同一リージョン内隔離保護（Zero Egress 構成）によるFinOps最適化設計を解説します。

---

## 1. 下りデータ転送費（Egress Cost）が招くコスト爆発の真実

パブリッククラウドの基本料金体系は「インバウンド（受信）無料 / アウトバウンド（送信・引き出し）高額」です。

- **200TB全データ外部引き出しの試算（東京リージョン）**:  
  インターネット経由で自社環境へ転送する場合、1GBあたり約0.09ドル。
  - **10TB**: 約 14万円
  - **100TB**: 約 140万円
  - **200TB**: **約 280万円**（※1回のフルバックアップデータ転送のみ）

> [!TIP]
> **FinOps ベストプラクティス**: データをオンプレミスへ全量持ち出すのではなく、**同一リージョン内の別AWSアカウント（隔離領域 / Rubrik Cloud Vault等）**へ保管。同一リージョン内転送を活用することでEgress費用を最小化・ゼロ化できます。

---

## 2. 大規模DBの構造的限界：標準RDSストレージ上限

通常の Amazon RDS (MySQL/PostgreSQL等) では、1インスタンスあたりの単一ストレージボリューム上限（最大64TB）が存在し、シャーディング（データベース分散分割）なしでの大規模スケールには限界があります。

---

## 3. Amazon Aurora による大規模環境の最適化

クラウドネイティブDB **[Amazon Aurora](https://fununi222.github.io/website/html/glossary/system-glossary.html#:~:text="Amazon%20Aurora")** は、ストレージエンジンがDBコンピュートから分離された分散アーキテクチャを採用しています。

- **シームレスなストレージ自動拡張**: 最大 128TB〜256TB（Aurora Limitless DB等）まで自動スケールアウト。
- **バックアップストレージ単価の優位性**: 標準RDSストレージ単価と比較して大幅なコスト削減（Auroraスナップショット保持費用の最適化）。
- **無停止バックグラウンドバックアップ**: 継続的なバックグラウンドバックアップにより、スナップショット取得時のI/O停止（Stun）や性能低下が発生しません。

---

## 4. まとめと推奨アクション

1. **Egress料金回避**: バックアップはインターネットへ出さず、クラウド内同一リージョン間隔離を基本とする。
2. **Aurora移行**: 単一ボリューム上限を超える前に、Auroraへアーキテクチャを統合。
3. **継続的FinOps評価**: コンピュート費用だけでなく、データ転送量・バックアップ保持費用のLTV（生涯価値）を算出。
